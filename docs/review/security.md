# Security Review
## Summary
The inherited environment is correctly allowlisted and shared by the Claude Max preflight and provider invocations, and the retained smoke artifacts showed no credential or raw-auth leakage. Two trust-boundary gaps remain: enterprise-managed Claude settings can restore provider-selection configuration, and the preflighted executable is not identity-bound to the executable later staged and launched.
## Findings
### 1. Managed Claude settings can bypass the credential and provider-selection boundary
- **Severity**: High
- **Location**: `internal/app/isolation_darwin.go:52`
- **Description**: Claude invocations deliberately grant the staged client read access to `/Library/Application Support/ClaudeCode`, the macOS location of `managed-settings.json`. The invoked `--safe-mode` does not disable admin-managed policy settings. Claude settings can define an `env` object containing `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_BASE_URL`, Bedrock/Vertex/Foundry selectors, model selectors, or an `apiKeyHelper`. Those values are loaded by Claude after `providerBaseEnvironment` has sanitized the inherited process environment, so the allowlist does not enforce the contract's Max-only/no-alternative-provider boundary on a managed machine. The preflight only validates three auth-status fields and does not validate the effective base URL, provider-selection settings, or model settings, so a `claude.ai` status does not close this path.
- **Evidence**: `isolation_darwin.go:52-55` adds the whole `/Library/Application Support/ClaudeCode` tree to `claudeClientReads`, and `isolation_darwin.go:134-137` grants that tree to the exact staged client. `agent_runner.go:158-165` passes `--safe-mode`, but local `rtk claude --help` (Claude Code 2.1.241) states: `Admin-managed (policy) settings still apply.` Anthropic documents `/Library/Application Support/ClaudeCode/managed-settings.json` as a highest-priority settings source and documents both settings-level `env` provider variables and `apiKeyHelper`. The passing command `rtk go test ./internal/app -run 'TestBlackBoxProviderProcessesNeverReceiveExternalCredentials|TestBlackBoxClaudeKeychainAccessIsProcessScoped|TestPromptAndStyleReadsRejectSymlinkComponents' -count=1 -v` reports `Go test: 3 passed in 1 packages`, but those tests cover ambient environment variables and filesystem access only; `rg` finds no managed-settings or `apiKeyHelper` test.
- **Suggestion**: Do not grant the Claude client the managed-settings tree. Allow only the exact regular authentication artifact(s) actually required for Max OAuth, through no-follow descriptors or identity-checked staged copies. If Claude cannot operate without consulting managed policy, fail closed after independently parsing and rejecting every managed setting capable of changing credentials, endpoint, provider, model, hooks, or helper execution; add a black-box case with managed `env` and `apiKeyHelper` values that must fail before run creation.

### 2. The executable that passes Max preflight is not bound to the bytes that are staged
- **Severity**: Medium
- **Location**: `internal/app/app.go:126`
- **Description**: The controller canonicalizes a Claude pathname and executes it for the Max preflight, but later `newTmuxRuntime` resolves and opens that pathname again to create the staged client. A pathname replacement or CLI auto-update between those operations can therefore make one executable pass authentication checks while different bytes are copied into the sandbox and receive the client-only Keychain/network/mach grants. A second lstat/open race exists inside `installPrivateRunner`, which checks the source and then opens it without verifying that both operations observed the same file.
- **Evidence**: `app.go:126-135` preflights `claudePath` and stores only its string pathname. `tmux.go:83-93` subsequently performs another `LookPath`/`EvalSymlinks`, and `tmux.go:137-142` copies from that path. `tmux.go:209-223` performs `Lstat(source)` followed by `os.Open(source)` without `os.SameFile`, a digest check, or a held descriptor. Thus the comment at `app.go:130-131` that the exact executable passing preflight is staged is not enforced by file identity.
- **Suggestion**: Open the resolved executable once with a no-follow operation, verify the opened descriptor is a regular executable and matches the resolved identity, stage from that held descriptor, and run the Max preflight against the immutable staged copy (before creating the durable run). Reuse those staged bytes for all single-use clients, or bind and verify a digest/inode identity across every copy.
